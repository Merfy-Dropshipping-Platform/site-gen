Эта страница описывает путь секции: файлы написаны → проверка → сохранение → публикация магазина и сборка → витрина.
На каждом шаге сказано, какая часть платформы работает и что остаётся, если шаг не прошёл.

Названия частей платформы:

- **шлюз** — единый вход API платформы (`gateway.merfy.ru`). Он проверяет, что запрос пришёл от мерчанта и что магазин
  принадлежит его организации;
- **sites** — сервис магазинов: ему шлюз передаёт запросы про секции и публикацию;
- **сборщик витрин** — отдельный сервис, который проверяет секции и собирает из них страницы магазина;
- **витрина** — готовый сайт магазина, который видят покупатели.

## 1. Написал: файлы секции

Исходник секции — набор файлов `section.json`, `template.astro` и, если нужен, `script.ts`
([из чего состоит секция](anatomy.md)). Файлы передаются в теле запроса как пары «путь — текст»,
общий размер не больше 512 КБ ([адреса и порядок работы](start.md#адреса)).

## 2. Проверка: ничего не записывается

Запрос «проверить» идёт через шлюз в sites, а оттуда в сборщик витрин. Шлюз проверяет права на магазин, sites — что
магазин создан на теме новой архитектуры, иначе ответ «магазина нет». Дальше сборщик:

1. Берёт файлы в отдельный процесс с жёсткими пределами: 10 секунд, 256 МБ памяти, пустое окружение. Сеть, запись
   файлов и запуск других процессов в нём закрыты. Время вышло или процесс упал — отказ `build-timeout` или
   `build-crashed`.
2. В этом процессе разбирает `section.json` (ключи, поля, блоки, имена из словаря), компилирует `template.astro`
   в модуль, который рисует HTML (запрещённые теги, неизвестные классы, слишком глубокие условия), и собирает
   `script.ts` (разрешённые импорты, имена из SDK).
3. Если замечаний нет, делает три пробных рендера шаблона: на значениях полей по умолчанию, на пустых значениях
   (мерчант может стереть любое поле) и на примерах данных магазина. Шаблон, который упал или вывел `[object Object]`,
   `undefined` или `NaN`, не проходит.

Ответ: `ok`, список `problems` (мешают сохранению) и `warnings` (предупреждения, например `taste-*`: секция сохранится,
но лучше исправить). У каждой записи — файл, строка, код и ссылка `doc` на разбор в [кодах ошибок](errors.md). Секция
с записью в `problems` в магазин не попадёт: та же проверка выполняется при сохранении.

## 3. Сохранение: секция становится черновиком магазина

Запрос «сохранить» проходит тот же путь и запускает ту же проверку заново. Если файлы совпадают с текущей
правкой секции, проверки и сборки нет, ответ `unchanged`. Иначе:

- проверка не прошла — ответ 422, ничего не записано;
- проверка прошла — скрипт загружается в хранилище файлов по отпечатку (sha256), а исходник и результат проверки
  записываются строкой в **реестр секций** (таблицу `storefront_section` базы sites). Ответ `accepted` с `id` правки.

Секция всегда принадлежит магазину из адреса запроса: тело запроса магазин не задаёт, лишние ключи в теле — отказ.
Если у секции есть роль (`role`) и в магазине уже есть другая секция с этой ролью, сохранение отклоняется
(`role-taken`).

Сохранённая правка становится **текущей** (черновиком): её видят список «Добавить секцию» и превью в конструкторе.
Витрина при этом не меняется. Предыдущие правки не удаляются: список правок и возврат к прежней — в
[адресах](start.md#адреса).

## 4. Публикация магазина и сборка

Мерчант публикует магазин. Это отдельное действие, и именно оно выводит секции на витрину:

1. Сервис sites отправляет сборщику событие «публикация» (`merchant-publish`) через очередь сообщений RabbitMQ и
   ждёт номер сборки до 3 секунд. Сборщик не ответил за это время — публикация записана как «в очереди», магазин
   соберётся, когда дойдёт очередь.
2. Перед сборкой сборщик **публикует черновики**: текущая правка каждой своей секции магазина получает отметку «на
   витрине», прежняя отметка снимается.
3. Сборщик делает снимок данных магазина: ревизию (страницы, их секции и введённые значения), настройки темы,
   товары, коллекции, статьи блога, политики и контакты. Из входов считается ключ сборки. Если ключ совпал с уже выложенной сборкой,
   пересобирать нечего.
4. Идёт сборка. Для каждой страницы шаблоны её секций рисуются в HTML с подставленными значениями — в отдельном процессе
   рендера. Из скриптов секций страницы и ядра SDK собирается один JavaScript-файл страницы (бандл); небольшой
   (до 4 КБ) вставляется прямо в HTML. Из классов в разметке собирается CSS.
5. Готовая сборка выкладывается в хранилище, и только после этого указатель магазина переключается на неё.

Что бывает при сбое:

- Секция не отрисовалась на странице — её на этой странице нет, сборка идёт дальше, ошибка пишется в журнал сборщика
  и в таблицу ошибок.
- Не отрисовалась секция с `"removable": false` или с ролью (шапка, подвал, корзина, вход) — сборка считается
  неудавшейся и не выкладывается. На витрине остаётся прежняя сборка.
- Любая другая ошибка сборки — тоже не трогает уже выложенный сайт: указатель переключает только последний шаг.

Сборка запускается не только публикацией: изменение товара, политики, контактов или настроек оплаты тоже ставит
опубликованный магазин на пересборку. Секции в этом случае берутся те же, что уже опубликованы.

## 5. Витрина: что получает покупатель

Покупатель получает готовые HTML-страницы, CSS и один JavaScript-файл страницы. Шаблоны в браузере не работают:
значения полей уже в HTML. В браузере запускается только скрипт: ядро SDK находит на странице секции, запускает
`mount` каждой, подключает действия `data-action` и события ([script.ts](script.md), [события](events.md)).

Ошибки скриптов секций в браузерах покупателей собираются и показываются в списке правок секции. Секция с ролью, у
которой за 15 минут набралось 10 ошибок и больше, сама возвращается к прежней опубликованной правке, а мерчант получает
уведомление ([порядок работы](start.md#порядок-работы)).

## Коротко

| Шаг               | Кто делает                         | Что меняется                                     |
| ----------------- | ---------------------------------- | ------------------------------------------------ |
| написал           | автор секции (человек или ИИ)      | ничего в платформе                               |
| проверка          | шлюз → sites → сборщик витрин      | ничего не записывается, ответ со списком замечаний |
| сохранение        | шлюз → sites → сборщик витрин      | новая текущая правка в реестре секций, витрина не меняется |
| публикация, сборка | sites → сборщик витрин             | черновики становятся «на витрине», собирается и выкладывается сайт |
| витрина           | браузер покупателя                 | HTML уже готов, запускается скрипт секции        |
