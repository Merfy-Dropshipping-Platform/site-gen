Секция — один блок страницы магазина: шапка, баннер, список товаров, подвал. Секция хранится как папка с файлами.
Описание нужно любой секции, разметка — обычной, скрипт — только той, у которой что-то меняется после загрузки. Эта страница объясняет, за что отвечает каждый файл, как они связаны и
откуда секция берёт данные. Подробные правила каждого файла — на страницах справочника, ссылки в тексте.

## Три файла

| Файл            | За что отвечает                                                       | Нужен ли                          |
| --------------- | --------------------------------------------------------------------- | --------------------------------- |
| `section.json`  | описание секции: имя, название, поля, блоки                           | всегда                            |
| `template.astro`| разметка: из чего состоит секция на странице и куда подставить данные | у обычной секции (`kind: section`)|
| `script.ts`     | поведение в браузере покупателя                                       | только если страница меняется после загрузки |

Рядом могут лежать `AGENTS.md` и `CLAUDE.md` — это подсказки для ИИ. Частью секции они не считаются: проверка и
сохранение их пропускают.

Есть и особая секция с `kind: global`. У неё нет места на странице и нет шаблона, только скрипт: он подключается к
страницам магазина сам, мерчант его не ставит.

### section.json — что видит мерчант в конструкторе

Мерчант — владелец магазина, он собирает страницы в конструкторе. Из `section.json` конструктор узнаёт три вещи.

- **Как секция называется.** Ключ `title` — название в списке «Добавить секцию». Ключ `name` — внутреннее имя секции:
  строчные латинские буквы и цифры через дефис. По нему секцию находят при сохранении и откате.
- **Какие настройки у неё есть.** Ключ `settings` — список полей. Каждое поле — это подпись для мерчанта (`label`),
  внутреннее имя (`id`) и вид (`kind` внутри `setting`): строка, текст, картинка, ссылка, переключатель, выбор из
  списка, ползунок, товар, коллекция и другие ([виды полей](section-json.md#виды-полей)). Конструктор показывает для
  каждого вида свой элемент: для строки — поле ввода, для переключателя — тумблер. Что мерчант ввёл, сохраняется в
  черновике его магазина.
- **Какие блоки в неё можно добавлять.** Ключ `blocks` описывает типы блоков: например, один вопрос со своим ответом в
  списке частых вопросов. У каждого типа блока свои поля и свой предел `limit` — сколько блоков этого типа можно
  добавить. Ключ `defaultBlocks` — какие блоки уже есть, когда секцию только добавили.

Имена полей берутся из общего словаря ([имена полей](names.md)): по имени платформа понимает, что в поле, и подсказывает
подходящий вид. Остальные ключи (куда секцию можно ставить, сколько экземпляров, какие данные нужны) — в
[справочнике по `section.json`](section-json.md#ключи).

### template.astro — разметка

Шаблон похож на обычный HTML с подстановками в фигурных скобках. Он написан на языке Astro, но с ограничениями:
переменных, функций и скриптов в нём нет ([что нельзя](template.md#что-нельзя)). Сборка магазина один раз превращает
шаблон в готовый HTML с настоящими значениями полей. Поэтому разметка приходит покупателю уже готовой, а шаблон в его
браузере не работает.

В шаблон попадают три набора данных (первая строка файла, `const { settings, blocks } = Astro.props;`):

- `settings` — значения полей, которые мерчант ввёл в конструкторе;
- `blocks` — блоки секции в том порядке, в котором мерчант их расставил;
- `theme` и `shop` — данные темы и магазина, только если секция попросила их ключом `uses` (ниже).

Внешний вид задают только классы из словаря ([классы и токены](styles.md)): своего CSS в секции нет.

### script.ts — поведение

Скрипт нужен, когда страница должна реагировать на покупателя: выбрать цвет, отфильтровать список, посчитать. Если
нужно только открыть и закрыть окно, переключить вкладку или прокрутить, готового поведения хватает без скрипта
([поведения](behaviors.md)).

Скрипт описывает секцию через `defineSection`: что делать, когда секция появилась на странице (`mount`), и какие
действия вызывает разметка. Прямого доступа к `window`, `document` и `fetch` у скрипта нет, всё идёт через объект `ctx`
([script.ts](script.md)); проверка не сохраняет секцию, которая обращается к ним напрямую.

## Как файлы связаны между собой

Связь идёт по именам.

1. **Поле в `section.json` ↔ значение в шаблоне.** Поле с `id: "heading"` в шаблоне читается как
   `settings.heading`.
2. **Блок в `section.json` ↔ `blocks` в шаблоне.** Типы блоков заданы в `section.json`, а шаблон выводит их списком
   через `blocks.map`.
3. **Разметка ↔ скрипт.** Скрипту нужны метки в шаблоне: `data-ref="имя"` помечает элемент, который скрипт найдёт через
   `ctx.ref("имя")`, а `data-action="имя"` связывает клик по элементу с действием в блоке `actions` скрипта. Значение из
   поля шаблон может передать скрипту через атрибут `data-*`.
4. **Данные из `uses` и `data` ↔ шаблон и скрипт.** Эти ключи `section.json` открывают секции данные (разбор ниже).

Часть имён проверка сверяет при сохранении: имя поля — со словарём, `data-action` в шаблоне — с действиями секции и SDK
(`action-unknown`), событие в `ctx.listen` — с каталогом событий (`event-unknown`), `ctx.data.<имя>` — с ключом `data`
(`data-unknown`). Список всех кодов — [коды ошибок](errors.md).

## Откуда секция берёт данные

Всё, что секция показывает или использует, приходит из трёх источников.

1. **Её собственные поля.** Мерчант заполнил — значение лежит в `settings`. Для поля вида «товар», «коллекция», «статья
   блога» или «политика» в шаблон приходят публичные поля выбранной записи магазина
   ([записи магазина в полях секции](data.md#записи-магазина-в-полях-секции)).
2. **Ключ `uses` в `section.json`.** Секция получает только то, что объявила:
   - `"theme"` открывает `theme` в шаблоне — сквозные настройки темы, общие для всего магазина: логотип, ссылки на
     соцсети, настройки корзины ([настройки темы](theme-settings.md)). Их мерчант меняет один раз для всех страниц.
   - `"shop"` открывает `shop` — публичные данные магазина: название, контакты, политики, признак «оплата онлайн»
     ([данные магазина](data.md)).
   - Имя модуля SDK (`cart`, `favorites`, `customer`, `auth` и другие) открывает в `script.ts` одноимённую часть `ctx`:
     корзину, избранное, вошедшего покупателя ([модули SDK](modules.md)). Модуль, к которому секция обращается
     действием в разметке (`data-action="cart.add"`), подключается сам, в `uses` его писать не нужно.
3. **Записи для скрипта.** Ключ `data` в `section.json` перечисляет, какие поля записи (например, товара страницы)
   нужны скрипту; они лежат в `ctx.data`.

Больше источников у секции нет. Прямых запросов на сервер она не делает: корзина, вход и заказы идут через модули SDK.
Данные, которых секция не объявила, она не увидит.

## Как секция общается со страницей

Секция и страница обмениваются двумя способами: действиями и событиями.

- **Действие** — команда от секции. В разметке пишется `data-action="cart.add"` на кнопке: клик по ней добавляет товар
  в корзину, скрипт для этого не нужен. Свои действия секции описаны в её `script.ts`. Список готовых действий и их
  ответы — [действия](actions.md).
- **Событие** — сообщение от страницы. Когда в корзину добавили товар или покупатель открыл страницу, ядро SDK
  отправляет событие вида `merfy:cart:add`. Скрипт секции подписывается на него через `ctx.listen` и обновляется.
  Данные события приходят копией, изменить исходные нельзя. Список событий и их данные — [события](events.md).
- **Свои события секции.** `ctx.emit("имя", данные)` отправляет событие `<имя секции>:имя`. Его можно слушать и
  в «Своём коде» мерчанта на странице магазина.

Что секция вправе делать при сохранении и сборке, ограничивают [лимиты](limits.md), а как проверка сообщает о
нарушениях — [коды ошибок](errors.md).
