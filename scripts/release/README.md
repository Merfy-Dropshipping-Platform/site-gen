# Поезд в прод

Одна команда вместо последовательности, которую 15 сентября выполнили руками
восемь раз по 10–20 минут. Последовательность детерминированная и отлажена —
здесь она записана целиком, вместе с местами, на которых мы уже спотыкались.

```bash
# посмотреть, что получилось бы (ничего не отправляет)
node scripts/release/train.mjs --branch fix/a --branch fix/b

# залить по-настоящему
node scripts/release/train.mjs --branch fix/a --branch fix/b --push --publish
```

По умолчанию команда **не пушит и не публикует**: собирает, проверяет и печатает,
что получилось бы. Пуш — `--push`, переопубликация стендов — `--publish`.

## Проверить локально: `pnpm checks`

```bash
pnpm checks               # только то, что задела правка; остальное из памяти
pnpm checks --plan        # ничего не гонять: что прогонится и почему
pnpm checks --full        # всё, без памяти (память обновится)
pnpm checks --audit       # всё, и сверить с памятью: ошибка памяти — провал
pnpm checks --skip-build  # не пересобирать (собрано этим же деревом)
```

То же, что поезд на шагах 4 и 6, но без git. Все гарды идут одним прогоном jest
на всех ядрах, кроме двух. Цикл `for i in 1..10; do ci-satin-guards.mjs --shard
$i/10; done` больше не нужен: это раскладка CI, где раннер двухъядерный, а на
ноутбуке она занимает два ядра из десяти и десять раз стартует с нуля.

**Память результатов** (spec 115, часть 3). Каждый прогон записывает, что
прочитала каждая проверка:

- модули её файла — реестр jest (`require.cache`), в том числе JSON и
  подгруженное динамически;
- файлы, прочитанные ею и вызванным кодом через `fs`;
- модули секций тёплого рендера — статическое замыкание импортов от модуля
  блока (второй вызов модуль не читает, поэтому по `fs` этого не узнать) и всё,
  что поток рендера читал через `fs` (с запасом);
- всё, что прочитали и загрузили дочерние `node`, — через
  `NODE_OPTIONS=--require scripts/release/lib/trace/child-preload.cjs`;
- снимок `__snapshots__/<файл>.snap`.

Если с тех пор не изменился ни один вход и общий ключ (lockfile, конфиг jest,
версия node, `PARITY_*`/`MERFY_*` в env, сами правила памяти), проверка прошла
бы так же: берётся прошлый зелёный результат с тем же числом проверок. Красное
не запоминается. Файл, который запускает процесс, чьи входы не записать
(`execSync`, `spawn` не-node), гоняется всегда. Память общая для всех worktree
(`~/.cache/merfy-checks/results`, пути относительные). Выход сборки хэшируется
без `compiledAt` и абсолютного корня дерева — то же правило, что у отпечатка
конформанса. CI памятью не пользуется: перед выкаткой гоняется всё.

Сборка пропускается, если её входы (themes, packages, src, скрипты сборки,
зависимости) не менялись с прошлой удачной сборки этого дерева.

Сомневаешься в памяти — `pnpm checks --audit`: гонит всё и падает, если
результат какой-то проверки разошёлся с памятью при том же ключе.

**Очередь на машину.** Полный прогон, поезд и любой большой jest (весь набор,
каталог или 4+ файлов) берут общий замок `~/.cache/merfy-checks/heavy.lock`.
Пока идёт соседний прогон, второй ждёт и раз в 10 с пишет, кого ждёт. Два
прогона разом идут медленнее, чем один за другим, и краснеют по таймаутам —
25.09 так падали `owner-default-sizes` и `hero-container-empty-state` без
единой ошибки в коде. Замок держит ядро (flock через perl): процесс умер — замок
снят, чистить нечего. Один-три файла jest идут без очереди. В CI очереди нет.
Выключить: `MERFY_CHECKS_LOCK=off`.

**Типы.** Локально ts-jest не проверяет типы (мелкий набор 3 с вместо 16).
В CI проверка типов осталась: ошибка типов в spec-файле красит CI, как раньше.

## Шаги

| № | Шаг | Что делает |
|---|-----|-----------|
| 1 | окружение | дерево чистое, ветка не `main`, взаимоисключающие флаги отсечены |
| 2 | состав | `git fetch origin main`; ветки, уже влитые в main, выкидываются из поезда; создаётся ветка поезда |
| 3 | мерж | вливает main и каждую ветку; конфликты в пяти накопительных файлах разводит скриптом, на конфликте в коде **останавливается** |
| 4 | пересборка | `build` → `build:blocks` → `build:theme-sections satin` → `run-theme-build satin` → `build:theme-sections:all` → `build:preview-tailwind` |
| 5 | инвентарь | `conformance:satin:refresh-inventory`; изменился — отдельный коммит |
| 6 | гарды | весь набор из `ci.yml` одним прогоном jest; печатает число прошедших проверок **по каждому** |
| 7 | гейт | `pre-push.sh` до строки «✓ гейт пройден» |
| 8 | свежесть | `origin/main` уехал — возврат к шагу 3 (до `--max-rounds`), а не пуш поверх |
| 9 | пуш | `git push origin HEAD:main` (только с `--push`) |
| 10 | CI | ждёт прогон **по своему SHA** через `gh api …/actions/runs` |
| 11 | стенды | публикует пять стендов и ждёт, пока `/build.json` покажет новый `sitesCommit` |

## Почему именно так

**Порядок сборки.** Кандидат инвентаря satin считается по результату
`run-theme-build satin`. Без этого шага локально зелено, а CI краснеет
«tracked inventory is stale» — поезд b13 (15.09) так потерял целый прогон.
`build:preview-tailwind` нужен раньше гардов: без бандла превью часть из них
не находит, что мерить.

**Числа у гардов.** `Tests: 0 total` даёт код возврата 0 и выглядит как успех.
Так же выглядит сюита, где все проверки `it.skip`. Поэтому считается не код
возврата, а количество **прошедших** проверок по каждому гарду; ноль —
остановка с именем гарда.

**Список гардов берётся из `ci.yml`, а не из константы.** Продублируй его в коде
— разойдётся в первый же день, и локальный прогон станет зелёным там, где CI
красный. Разбор построчный: тащить YAML-парсер ради шести ключей нельзя.
Цепочки `pnpm a && pnpm b` разбираются на звенья, иначе ноль проверок во второй
половине пройдёт мимо счётчика.

**Про чужие workflow команда говорит вслух.** Кроме `ci.yml` судьбу прогона
решает `theme-parity.yml` (Playwright + отдельный репозиторий эталонов). Локально
он не гоняется — и команда честно печатает это строкой, а не молчит: «зелено
локально» не равно «зелено в CI».

**Статус CI спрашивается по своему SHA.** `gh run list` отдаёт срез, в котором
сверху лежат чужие и старые прогоны — 15.09 это дважды подняло ложную тревогу
про красный CI.

**Стенды.** Витрина собрана заранее: пока стенд не переопубликован и его
`/build.json` не показал новый `sitesCommit`, обсуждать поведение бессмысленно.
Публикация идёт **только по http** — сертификат на имени sites-сервиса выписан
на прежний адрес.

## Конфликты

Разводятся ровно пять накопительных файлов, где обе стороны дописали своё:

| Файл | Правило |
|------|---------|
| `docs/theme-work/STATUS.md` | обе стороны, наша первой |
| `docs/theme-work/WORKLOG.md` | обе стороны, наша последней |
| `.github/workflows/ci.yml` | оба шага сохраняются |
| `package.json` | оба скрипта, с проверкой валидности JSON |
| `conformance/inventory/satin.generated.json` | берётся из main, затем перегенерация на шаге 5 |

Всё остальное — **код**. На нём `resolve-merge.py` честно падает, мерж
откатывается (`git merge --abort`), команда называет файл и останавливается.
Угадывать, чья версия кода верна, инструмент не будет.

## Остановки

Каждая печатает причину и что делать человеку:

* конфликт в коде — имя файла и порядок ручного мержа;
* ноль проверок у гарда — имя гарда и его команда;
* красный гард — имя и хвост вывода;
* красный гейт — что именно он показал;
* уехавший main — сколько коммитов приехало;
* красный CI — ссылки на логи и напоминание не пушить поверх.

## Флаги

```
--branch / --branches   состав поезда (без них — текущая ветка)
--train-branch          имя собираемой ветки
--onto                  база (по умолчанию origin/main)
--push                  реально пушить в main
--publish               переопубликовать стенды (нужен --push)
--guards ci|none|файл   набор гардов; none вместе с --push запрещён
--guard <команда>       добавить гард к набору (повторяемый)
--skip-build            не пересобирать (только если собрано этим же деревом)
--skip-gate             не гонять гейт; вместе с --push запрещён
--max-rounds            сколько раз перезаходить, если main уехал (2)
--ci-timeout            минут ждать CI (30)
--publish-timeout       минут ждать витрины (10)
--stands / --gate       пути к stands.json и pre-push.sh
--json <файл>           машиночитаемая сводка
--verbose               вывод команд целиком
```

## Чего команда НЕ делает

* **не решает конфликты в коде** — останавливается и отдаёт человеку;
* **не обновляет снимки разметки** (`-u`): расхождение снимка — это либо
  осознанная правка, либо регрессия, и решает это человек;
* **не двигает базовую линию конформанса** (`--shrink-baseline`);
* **не ревьюит содержимое веток** — что попало в поезд, решает человек;
* **не чинит красный CI** — приносит ссылку на логи;
* **не публикует стенды без `--push`** и без зелёного CI;
* **не пушит ничего, кроме main**, и только по явному флагу.
