# @merfy/storefront-config

Конфиг витрины новых тем: данные магазина для страницы — id и имя магазина, его адрес, адрес API, валюта, язык, тема
и страница. Конфиг лежит в `<head>` страницы JSON-тегом `<script type="application/json" id="merfy-config">`, скрипты
читают его сразу, без запроса. Нынешние темы (rose, vanilla, flux, satin, bloom) его не используют. Проработка —
`merfy-mcp/docs/plans/storefront-shell/03-config/design.md`.

Пакет — исходники TypeScript без сборки. Правила конфига записаны в одном месте — схеме zod в `src/schema.ts`. Тип
`StorefrontConfig` выводится из неё, а JSON Schema в `generated/` пишет команда `generate`.

## Команды

Из папки пакета:

- `pnpm test`, `pnpm test:coverage` — тесты пакета; порог покрытия — 80 %;
- `pnpm test:stand` — сборка темы `nova` со стендом: тег в `<head>`, его разбор, без флага тега нет. Нужна установка
  темы: `pnpm install --ignore-workspace` в `themes/nova`;
- `pnpm typecheck`, `pnpm lint`, `pnpm format:check`;
- `pnpm generate` — пишет `generated/*.schema.json` из схем zod. Руками эти файлы не правят: тест расхождения
  сравнивает их с генерацией.

## Как читать конфиг

В браузере конфиг читает отдельный вход `src/read.ts` (`@merfy/storefront-config/read`). zod в нём нет, это
сторожит линтер: в скрипт страницы zod не попадёт.

```ts
import { readStorefrontConfig } from '@merfy/storefront-config/read';

const config = readStorefrontConfig(); // ищет #merfy-config в document
```

Читатель проверяет версию формы (`v: 1`), обязательные поля и их типы. Ошибка — `StorefrontConfigError` с кодом и
путём поля: `config-missing` — тега нет; `config-version` — другая версия формы; `config-invalid` — в теге не JSON или
поле не того типа. Запасных значений у читателя нет. Что делать при ошибке, решает вызывающий: стенд показывает текст
ошибки в разделе «Конфиг магазина» и пишет его в консоль.

Полной схемой конфиг проверяет писатель при сборке страницы: `buildStorefrontConfig({ site, theme, env, page, mode })`.
Не прошёл схему — сборка падает с ошибкой, которая называет поле: `shop.url: у опубликованного магазина нужен адрес`.
Строку тега даёт `configTag(config)`; тег ставится в `<head>` раньше любого скрипта.

## Как добавить поле

1. Поле — в схему `src/schema.ts`. Новое поле версию формы не меняет. Ломающее изменение — убрать или переименовать
   поле, сменить его тип — это `v: 2` и новый читатель.
2. Писатель `src/build.ts`: значение берётся из входа поле за полем, вход целиком не раскладывается.
3. Читатель `src/read.ts`: строка в таблице `FIELD_CHECKS`, если без поля каркасу не обойтись.
4. Эталон стенда: `fixtures/stand-input.json` и `fixtures/stand-config.json`.
5. `pnpm generate`, затем тесты. В тестах схемы неверное значение нового поля даёт ошибку с путём поля.

В конфиг идёт только то, что одинаково для всех покупателей магазина и что кто-то читает.

## Как добавить событие

События, после которых магазин пересобирается, лежат данными в `rebuild-events.json`, схема — в `src/events.ts`.
Одна запись — одно событие:

- `id` — латиница в kebab-case; `title` — что случилось, по-русски;
- `trigger` — откуда событие. Источник в site-gen — `file` (путь от корня репозитория) и `name` (имя сообщения или
  функции). Источник в другом сервисе (product, billing, inventory) — `service` и `description`: его код site-gen
  прочитать не может. `null` — кода ещё нет;
- `themes` — `all` (и нынешние темы) или `new` (только новые);
- `scope` — что пересобрать: `store` — весь магазин, `dependent-pages` — страницы, которые зависят от изменённых
  данных, `theme-stores` — все магазины на этой теме;
- `delayMs` — задержка перед пересборкой; `status` — `works` (работает сейчас), `block-10` (сделает этот блок),
  `with-sections` (издатель встанет вместе с секциями, когда эти данные появятся на страницах новой темы).

Тест читает файл из `trigger.file` и ищет в нём `trigger.name`: переименовали функцию — тест красный. У источника в
другом сервисе файл не сверяется. Задержка, которая есть в коде константой, сверяется с ней тестом. После правки схемы
событий — `pnpm generate`.
