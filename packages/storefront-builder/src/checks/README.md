# Места проверок

Владелец 16.11: проверки не должны лежать вразнобой — у каждой своё место, сегодня семантика, завтра Lighthouse.
Место выбирается по тому, что проверке нужно на входе. Схема и все шесть мест — страница «Каркас и проверки».

| Место     | На входе                                                                    | Где живёт                            |
| --------- | --------------------------------------------------------------------------- | ------------------------------------ |
| `code`    | файлы секции                                                                | `storefront-sections` (приём секции) |
| `html`    | готовый HTML страницы, без браузера                                         | `checks/html/`                       |
| `browser` | открытая страница в Chromium                                                | `checks/browser/`                    |
| `audit`   | отдельный прогон опубликованной страницы (Lighthouse со временем LCP и FCP) | пока нет                             |
| `shop`    | данные магазина перед публикацией                                           | пока в merfy-mcp `publish.ts`        |
| `release` | главная «до» и «после» выпуска                                              | `stand-check` (паспорт)              |

## Как устроено

- Одна проверка — один файл в папке места и свой тест: маленький HTML с ошибкой и без.
- Находка — один вид на все места: `CheckFinding` в `finding.ts`
  (`place`, `check`, `rule`, `level`, `section`, `where`, `text`, `count`, `fix`). `text` — «что не так · как починить».
- `fix` — кто чинит: `silent` (агент молча), `ask` (данные магазина — предложить мерчанту и спросить), `platform`
  (чинит платформа, агенту не показывается). Значение по месту — таблица `FIX_BY_PLACE` в `finding.ts`: code, html,
  browser, audit — `silent`; shop — `ask`; release — `platform`. Проверка с исключением задаёт `fix` сама. В ответе
  поле заполнено всегда.
- Секции платформы (19.11): платформенная — библиотечная секция, которую в магазине не меняли. Находка в ней получает
  `fix` по таблице `FIX_ON_PLATFORM_SECTION`: `silent` → `platform`, `ask` остаётся. Секции нашей библиотеки лежат в
  магазине как свои (`shop:…`), поэтому признак — файлы: отпечаток правки секции (`libraryKeyOf`) есть в индексе
  библиотеки (`isLibrarySection`, `storefront-sections`). Файлы знает только реестр, поэтому отбирает превью
  (`platformIdsOf` в `preview-sample.ts`, запрос `libraryUnchanged`) и кладёт id экземпляров в тег снимка
  `merfy-look-sample` (поле `platform`); снимок читает их через `html/platform.ts`, а `checksOn` (`look/look-job.ts`)
  применяет ко всем находкам разом. Изменённая библиотечная и своя секция, в том числе с ролью (`data-role`), остаются
  агенту: он мог написать свою корзину.
- Сводка Web Vitals `checks.vitals` (`device`, `cls`, `tbtMs`, `limits`, `lcp`) идёт рядом с `findings` и `failed` в
  снимках страницы и секции; пороги `limits` — из `VITALS_LIMITS` для устройства замера (первое в снимке). Замера нет
  (сбой, таймаут) — поля нет.
- Важность ставит проверка, последствие решает момент: семантика, Web Vitals и Lighthouse — всегда `warning`,
  публикацию не блокируют.
- Проверка находит по всей странице, отбор по секциям — `inSections`: в снимке секций — только изменённые секции
  (`sections` задания снимка = `checkScope` записи в sites), в снимке страницы — все.
- Проверка упала — это не находка, а `CheckFailure` с причиной; остальные проверки и снимок идут дальше.

## Что сейчас

- `html/semantic.ts` — html-validate: порядок и пустые заголовки, role вместо тега, кнопки и ссылки без текста,
  картинки без alt; своё правило `product-photo-alt` (фото товара с пустым alt). Содержимое `<template>` не
  проверяется (18.11): это заготовки строк для скрипта секции, браузер их не рисует, поисковик не читает.

Базовые секции (`storefront-sections/fixtures/shop`, `storefront-shell/sections`) 18.11 доведены до нуля находок на
страницах нового магазина: шапка и подвал — в ориентирах `<header>` и `<footer>` (ставит сборка, `pageLocals` в
`storefront-build/src/head.ts`, и живое превью), h1 главной — логотип в шапке, у оформления заказа — свой h1.

- `browser/semantic.ts` — axe-core: ориентиры (header, main, footer), списки, недопустимые role, вложенные кнопки.
- `browser/vitals.ts` — Web Vitals загрузки черновика (18.11): CLS и секция, из-за которой прыгает вёрстка (та, что
  выросла, а не сдвинутая ниже); главный элемент первого экрана (LCP) и что его задерживает: вставлен или показан
  скриптом, адрес ставит скрипт, фон в CSS, `loading="lazy"`; TBT и секция с тяжёлым запуском. ЦП телефона замедлен, как
  в Lighthouse. Пороги — «хорошо» у Google: CLS до 0,1, TBT до 200 мс на телефоне и до 150 мс на компьютере. Время LCP и
  FCP по черновику врёт (превью зашивает стили и скрипты в страницу) — его будет мерить место `audit`.
- `browser/lighthouse.ts` — Lighthouse 13 (как в PageSpeed) в режиме snapshot по той же вкладке, без перезагрузки:
  картинки без размеров, растянутые картинки, ссылки, по которым не пройдёт поисковик, запрет вставки в полях.
  Подключение к вкладке — `look/look-audit.ts`. Прогоны идут по одному на процесс (19.11): Lighthouse ведёт замеры
  через глобальный `performance` и при двух прогонах разом падает с `lh:runner:gather`. Ждущий ждёт очереди в пределах
  своего срока; не дождался — проверка в `failed` с причиной «очередь Lighthouse занята другим снимком».

Запускает их снимок черновика (`look/look-job.ts`, поле `checks` ответа). Находки детектора и проверок вёрстки пока
идут прежним полем `findings` — переедут сюда отдельной задачей.

## Новая проверка

1. Файл в папке своего места: функция «вход места → `CheckFinding[]`», тексты по-русски.
2. Тест рядом с остальными (`__tests__/checks-*.test.ts`).
3. Вызов в раннере места: для `html` и `browser` — `checksOn` в `look/look-job.ts`.
   MCP менять не нужно: он показывает `checks` одним кодом.
