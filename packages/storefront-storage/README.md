# @merfy/storefront-storage

Хранилище по хэшу и указатель магазинов новой темы: файл сборки лежит один раз на платформу, сборка — её манифест и
таблица раздачи, указатель «магазин → живая сборка» переключается одной условной записью, откат — за секунду. Нынешние
темы (rose, vanilla, flux, satin, bloom) и их публикация этим пакетом не пользуются. Проработка —
`merfy-mcp/docs/plans/storefront-shell/05-storage-pointer/design.md`. То, что пишет пакет, раздаёт nginx-minio-proxy,
папка `storefront/`.

Пакет — исходники TypeScript без сборки. Сборщика, очереди и рисовальщика здесь нет: их делает блок 6.

## Команды

Из папки пакета:

- `pnpm test`, `pnpm test:coverage` — быстрые тесты, хранилище в памяти; порог покрытия — 80 %;
- `pnpm minio:up`, `pnpm minio:stop` — MinIO для тестов (`compose.minio.yml`, порт 19100, та же версия, что на dev и в
  проде); `pnpm test:minio` — тесты на нём;
- `pnpm typecheck`, `pnpm lint`, `pnpm format:check`;
- `pnpm probe:pointer` — проба условной записи на MinIO;
- служебные команды — хранилище из переменных окружения `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`
  (значения не печатаются):
  - `pnpm publish:stand --from <папка> --label <метка> [--build N] [--public-url URL] [--indexable] [--allow <правило>]`
    — выложить магазин-стенд, собранный `pnpm build:stand` пакета `@merfy/storefront-build`;
  - `pnpm pointer show|rollback|pause|resume --label <метка> [--from N]` — указатель: показать, откатить с живой
    сборки N на прошлую (выкладка встаёт на паузу), поставить на паузу, снять паузу;
  - `pnpm cleanup [--apply]` — уборка; без `--apply` только показывает, что удалила бы.

## Где что лежит

Всё — под `storefront/` бакета `merfy-sites`, рядом с нынешним `sites/`:

| Ключ | Что |
|---|---|
| `blobs/<2 знака>/<sha256>` | файл сборки по отпечатку содержимого |
| `manifests/<магазин>/<сборка>.json` | манифест сборки (блок 4) |
| `routes/<магазин>/<сборка>.json` | таблица раздачи: «путь → отпечаток, тип, кэш, дата правки», `moved` (301), `gone` (410 до даты), `notFound`, `versions` |
| `drawn/<магазин>/<сборка>.json` | список дорисовок сборки |
| `entities/<магазин>.json` | список адресов сущностей магазина |
| `pointers/<метка хоста>.json` | указатель: `build`, `newest`, `rev`, `paused`, `pending`, `history` |

Форматы — схемы в `src/formats.ts`, версия 1. Их читает раздача (`storefront/njs/route.js` в nginx-minio-proxy): поменял
формат — поменяй и её.

## Как устроено

- **Выкладка** (`publishBuild`): манифест проходит схему блока 4 → заливка только нового (`src/upload.ts`): файлы
  прошлой живой сборки не льются, перерисованные — льются, у хранилища спрашивается только то, чего нет ни там, ни там →
  проверка перед переключением (`src/publish-rules.ts`) → манифест и таблица раздачи с `robots.txt` и картой сайта →
  указатель одной условной записью. Сборка не новее уже выложенных — `stale`, ничего не пишет.
- **Указатель** (`src/pointer.ts`): что делает каждая команда, решает чистая функция `nextPointer`; запись —
  `updateObject` с `If-Match` и повтором. «Только если новее» сравнивает с `newest`. Откат ставит выкладку на паузу:
  новые сборки ждут в `pending`, снятие паузы выкладывает ждущую. `rev` растёт с каждой записью: отпечаток S3 — хэш
  содержимого, и без `rev` повтор того же состояния пропустил бы запись по старому отпечатку.
- **Таблица раздачи** (`src/routes-table.ts`): каждый файл — по пути от корня, страница — ещё и по адресу, с датой
  правки её данных. Переезды и удалённое — из разницы с прошлой живой сборкой: у сущности с одной страницей сменился
  адрес — 301; удалили товар, коллекцию или публикацию — 410 на полгода; остальное — 404. Страница 404 темы — файл
  `404.html`.
- **Списки**: дорисованную страницу (`recordDrawnPage`) кладёт рисовальщик — файл и строку в список живой сборки;
  адреса новых сущностей (`addEntityPaths`, `removeEntityPaths`) ведёт сборщик.
- **Уборка** (`src/cleanup.ts`): хранит последние 5 сборок магазина, последнюю каждой из 3 последних пар «рендер +
  тема», всё моложе суток и всё, на что смотрит указатель; файлы без ссылок старше суток удаляет.
- **«Живая сборка есть?»** (`hasLiveBuild`) — для фоновых задач нынешнего конвейера: у магазина новой темы есть
  указатель.

## Как добавить правило проверки

1. Строка — в `PUBLISH_RULES` (`src/publish-rules.ts`): имя, текст, можно ли разрешить служебной командой, проверка.
2. Имя — в тип `PublishRuleId` и в тест «у каждого правила — имя и текст».
3. Тест на правило — в `__tests__/publish-rules.test.ts`: сборка, на которой оно срабатывает, и та, на которой нет.
