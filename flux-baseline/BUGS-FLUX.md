# Баги Flux — с голоса владельца, сессия 2026-08-02

Формат: владелец наговаривает, диктофонный текст транскрибируется сюда как
отдельные пункты. Каждый пункт — то, что реально увидел в конструкторе на
`http://localhost:3200/?siteId=132d3a3e-a28f-40b7-98fa-a0200151cfb8`.

**Эталон поведения — Roza.** Секции у Flux и Rose используют один и тот же
`puckConfig` (общий из `theme-base`) — набор полей идентичен. Задача не
«придумать», как должна работать настройка, а **скопировать поведение Rose**.

## ⚠️ Методологическая находка (важно для того, кто чинит)

Прошлая проверка (`flux-baseline/settings-liveness2.mjs`) сверяла только
`render(A) !== render(B)` — «два значения дают разный HTML». Это **не
доказывает, что хотя бы одно из них корректно**. Оба значения могли быть
одинаково сломаны (например, оба прячут контент, но по-разному) — матрица
всё равно засчитывала это как «живая настройка».

Прямая проверка (2026-08-02, `Hero.position=top-left` + реальные
heading/text/primaryButton через `/preview/block`) показала: **контент
присутствует в HTML** серверного рендера. Значит баг — не в том, что вёрстка
теряет данные при простом SSR-рендере с валидными пропами. Вероятные места:

- путь живого превью (`update-block`/`reconcile` в iframe, hot-patch без
  полной перезагрузки) — расходится с первым SSR;
- реальные пропы, которые пишет UI-контрол конструктора, ПО ФОРМЕ отличаются
  от того, что я скармливал руками (нужно смотреть реальную ревизию в БД
  после правки через UI, а не гадать);
- CSS/раскладка — контент в DOM есть, но визуально невидим/съехал.

**Для каждого пункта ниже — исправление проверять ЖИВЫМ путём**: открыть
конструктор → включить настройку через UI → посмотреть на реальный прогон
(превью **и** посмотреть `site_revision.data` в БД, что там реально легло) →
только потом чинить порт. Не полагаться на прямой `/preview/block` с
самодельными пропами как на единственное доказательство.

## B1 — Hero: белый экран после перезагрузки страницы

**Секция:** Изображение (Hero)
**Действие:** владелец перезагрузил страницу конструктора.
**Результат:** секция Hero — полностью белый экран, ничего не рендерится (не
плейсхолдер «Изображение», а именно пусто).
**Дальше:** пытался заменить фото — загрузка.

**Статус: root cause НЕ подтверждён эмпирически, несмотря на исчерпывающее
расследование. Применена защитная мера (не «исправление первопричины»).**

Нашёл по логам sites.log точный момент бага: reload в 15:31:24-25 UTC
2026-08-02, ПЕРЕД любой загрузкой фото (первое фото загружено только в
15:31:53). На тот момент активная ревизия (`site.current_revision_id` в БД
на тот момент = `c48f39d7-e7e1-4a89-acfe-97d2f5b4e7f8`) имела Hero-пропы:
```json
{"id":"Hero-home","backgroundImages":{"url1":"https://minio.merfy.ru/product-images/f92e309e-009c-4e15-85cc-87a59a439dea.png?e2eSeed=0"}}
```
(остаточные e2e-seed данные — заголовок/текст/кнопка НЕ заданы, должны падать
на REF_* дефолты Hero.astro).

Проверено 3 независимых способа воспроизвести — ВСЕ дают корректный рендер:
1. Изолированный `/preview/block` с этими пропами → h1/p/a на месте.
2. Полный `/preview?page=home` (реальный pipeline: `migrateRevisionData` +
   composeContentPagesIntoDist) — временно указал `site.current_revision_id`
   на копию ревизии с этими Hero-пропами (данные СНАЧАЛА забэкапил, после
   теста восстановил байт-в-байт — подтверждено diff'ом, удалил тестовую
   строку из `site_revision`) → h1/p/a на месте, фото грузится (imgComplete,
   naturalWidth=1500).
3. Живой Playwright reload той же ревизии с реальной сессией (тестовый
   аккаунт `flux-e2e-test-local@example.com`) → в iframe DOM: h1 текст
   присутствует, `color: rgb(0,0,0)` (видимый), картинка загружена.

Логи sites.log за 15:31:24-25 тоже показывают `request completed` без ошибок
для `get_site`/`puck-config`/`preview?page=home` — сервис не падал и не
перезапускался (процесс работал непрерывно с 15:00 без «Starting Nest» между).

Проверенные и ОТКЛОНЁННЫЕ гипотезы:
- Несовпадение форм пропов (`heading` vs `title` и т.д.) — код Hero.astro уже
  корректно проверяет ОБЕ формы через цепочки `nonEmpty(...) ?? ...`.
- `.color-scheme-N`-обёртка красит текст в белый на белом — ОПРОВЕРГНУТО:
  честный HTML-парсер (не глазами по минифицированному HTML) показал, что
  `<section data-puck-component-id="Hero-home">` — ПРЯМОЙ ребёнок `<main>`,
  без единой `.color-scheme-N`-обёртки в цепочке предков.
- `revision-migrations.ts` `clearDemoImageSections` стирает demo-фото — ОПРОВЕРГНУТО:
  `DEMO_IMAGE_URLS` содержит URL БЕЗ `?e2eSeed=0`, точное сравнение строк не
  совпадает с фактическим значением (есть хвост) → миграция не применяется.
- `data-reveal`/GSAP scroll-reveal анимация (`.has-js [data-reveal]{opacity:0}`
  до срабатывания ScrollTrigger) — правдоподобно объясняет «текст пропал», но
  НЕ «абсолютно пусто»: фон-фото и placeholder-ветка НЕ обёрнуты в
  `data-reveal`, должны быть видны в любом случае.
- `buildPuckConfig`-фейл (SiteConstructor.tsx) вешает весь редактор на
  `<LoadingOverlay>` навсегда без ретрая — реальный пробел в коде, но логи
  ПРЯМО показывают, что `GET puck-config` в момент бага завершился успешно →
  не может быть причиной именно этого эпизода.

**Единственный механизм, который объясняет ИМЕННО «абсолютно пусто, не
плейсхолдер, не текст ошибки»** — сбой самой сетевой навигации iframe
(connection reset/timeout/пустой ответ): тогда до Hero.astro дело не доходит
вовсе. У `<iframe>` в `PreviewFrame.tsx` не было НИ `onError`, НИ retry, НИ
видимой обратной связи — молчаливый белый экран навсегда, если такое
случится. Это подтверждённый чтением кода пробел (не гадание о точном
триггере B1).

**Применено (`PreviewFrame.tsx`):** watchdog-таймер 12с на `ready`-сигнал
агента + `onError` на iframe → до 3 автоматических ретраев с cache-bust
query-параметром → после исчерпания — видимый оверлей «Не удалось загрузить
превью» с кнопкой «Повторить». Существующий тихий reload при `reconcile-ack`
неудаче переведён на тот же механизм (раньше мутировал `iframe.src` напрямую
в обход React-состояния — при следующем ре-рендере это откатилось бы).

⚠️ **Это НЕ доказанное исправление первопричины B1** — это защита от
единственного оставшегося правдоподобного механизма. Если баг повторится —
теперь будет видимый `console.warn` с номером попытки + кнопка «Повторить»
вместо молчаливой пустоты, что даст материал для дальнейшей диагностики.

## B2 — Hero: «Размер» меняет только высоту, пропорция фото едет

**Секция:** Изображение (Hero) → поле «Размер» (small/medium/large)
**Результат:** при смене размера меняется только высота полотна; сама
фотография не сохраняет пропорции — визуально «плющится»/съезжает кадр.
**Вероятная причина (нужно подтвердить живьём):** кадрирование в
`Hero.astro` для одиночного фото использует ЛИТЕРАЛЬНЫЕ проценты
(`top-[-10.8%]`, `w-[200%] sm:w-[160%]`), откалиброванные под ОДНУ
конкретную высоту (large: 380/480/аспект 1920×810 у верстальщиков). При
переключении на medium/small контейнер уменьшается, а обрезка фото
пересчитывается НЕ пропорционально — крой уезжает.
**Файл:** `themes/flux/src/components/sections/Hero.astro` (ветка с
одиночным `backgroundImage`, ~строка 350).
**Как у Rose:** посмотреть `themes/rose/src/components/sections/Hero.astro`
— скорее всего кадрирование там завязано на CSS-переменную/aspect-ratio, а
не на литеральные проценты одной высоты.

## B3 — Hero: «Позиция» — весь текстовый блок пропадает ✅ ИСПРАВЛЕНО

**Root cause (подтверждён живьём, Playwright + computed-style):** НЕ в
`Hero.astro` вообще — общетемный баг reveal-анимации. `.has-js [data-reveal]
{opacity:0}` (global.css:76) прячет контент ДО срабатывания GSAP
`ScrollTrigger.batch` (`themes/flux/src/lib/animations.ts` `initAnimations()`,
вызывается ОДИН раз из `Layout.astro` при первой загрузке). Смена «Позиция» →
`update-block` → `preview.service.ts` `el.outerHTML = html` (полная замена
секции) → СВЕЖИЙ DOM-узел `[data-reveal]`, которого исходный ScrollTrigger не
видел → застревает на `opacity:0` НАВСЕГДА (даже после прокрутки — batch
одноразовый и уже отработал по старым узлам). Пруф: computed opacity ДО клика
= `"1"`/`transform: matrix(1,0,0,1,0,0)`, ПОСЛЕ смены позиции = `"0"`/
`transform: none` — ровно необработанное CSS-состояние.

**Как нашли:** прямой SSR (`/preview/block`) и полный composed page ВСЕГДА
рендерят корректно (root cause не в разметке/пропсах) → значит дело в
CLIENT-SIDE пути. Первые Playwright-попытки дали ложный «баг» из-за
слишком широкого CSS-селектора (`:has-text()` в комбинации с запятой мог
кликать не туда) — переделал на точный `locator().filter({hasText})`, тогда
воспроизвёл честно.

**Эталон-прецедент (уже решён для ДРУГОГО механизма):** rose использует
`data-animate` + `IntersectionObserver` (НЕ GSAP) и уже чинит ТОТ ЖЕ класс
бага повторным вызовом `initScrollAnimations()` на `astro:after-swap`
(`themes/rose/src/layouts/Layout.astro:135-136`). `astro:after-swap` УЖЕ
диспатчится после каждого hot-replace (`preview.service.ts`
`executeScriptsIn` → `dispatchAstroNavEventsDebounced`) — просто GSAP-реализация
flux не была на это подписана.

**Фикс:** `themes/flux/src/lib/animations.ts` — фильтр `:not([data-reveal-bound])`
(и `-group-bound` для групп), помечаем обработанные элементы, чтобы повторный
вызов НЕ откатывал уже показанный контент (в отличие от идемпотентного
`classList.add` у rose, `gsap.set()` на уже раскрытом узле сбросил бы его
обратно). `themes/flux/src/layouts/Layout.astro` — `document.addEventListener
("astro:after-swap", () => initAnimations())` рядом с исходным вызовом.

**Затрагивает ВСЕ секции с `data-reveal`** (theme-wide фикс, не Hero-специфичный):
`Collections.astro`, `Gallery.astro`, `Hero.astro`, `FeaturedProduct.astro`,
`Puk.astro`, `Popular.astro` — то есть потенциально закрывает ТАКЖЕ B4/B5
(Collections) и B7 (PopularProducts), возможно и часть B6 (Product). Каждый
из них ниже перепроверен ОТДЕЛЬНО живым Playwright-прогоном, а не по аналогии.

**Verified:** 4 живых перехода позиции подряд (top-right→bottom-center→
center→top-left) через реальный dropdown в сайдбаре — h1 остаётся видимым и
корректно позиционированным на каждом шаге (screenshot + computed opacity).

## B4/B5 — Collections: «Заголовок»/«Текст» пропадают ✅ ИСПРАВЛЕНО (тем же фиксом что B3)

**Root cause:** ТОТ ЖЕ theme-wide баг, что и B3 (см. выше) — `Collections.astro`
тоже оборачивает контент в `data-reveal`, тоже проходит через
`update-block`/`el.outerHTML=html` на правку поля → свежий узел без reveal →
`opacity:0` навсегда. Не Collections-специфичный баг, не про поля heading/
subtitle конкретно.

**Verified живьём** (реальные поля сайдбара, НЕ угаданные — `#heading`
`<input>`, `#subtitle` `<textarea>`, найдены через DOM-инспекцию панели, а не
предположение о типе поля): заполнил `#heading`="РЕАЛЬНЫЙ ЗАГОЛОВОК
КОЛЛЕКЦИЙ" → сразу виден на холсте (opacity 1). Заполнил `#subtitle`=
"Реальный текст-описание под заголовком коллекций" → сразу виден. Скриншот
подтверждает оба текста на канвасе синхронно с сайдбаром.

**Урок теста:** первая попытка проверки промахнулась мимо полей (xpath
`following::textarea` нашёл не тот элемент — поле «Заголовок» на деле
`<input type="text">`, НЕ textarea; получил ложный «баг» — записал текст не в
то поле). Правило подтверждено ещё раз: не гадать структуру поля, смотреть
реальный DOM (`evaluate` + `outerHTML` конкретного field-wrapper'а) перед тем
как писать локатор.

## ⚠️ Кэш dist/theme-sections — обязательный шаг после КАЖДОЙ правки .astro

`/preview/block` (и весь v2-рендер) импортирует НЕ `themes/<t>/src/...` напрямую,
а скомпилированный `dist/theme-sections/<t>/*.mjs` (манифест
`dist/theme-sections/<t>/manifest.json`, генерируется `compile-theme-sections.mjs`
— ОТДЕЛЬНЫЙ от `build:themes`/`ThemeBuildService` шаг). Правка исходника
`.astro` НЕ видна в рендере, пока не пересобран именно этот артефакт:

```bash
node scripts/compile-theme-sections.mjs flux   # ~2с, конкретная тема
```

Кэш-бастинг там УЖЕ умный (mtime в query `?v=<mtime>` при `NODE_ENV!==production`,
см. `preview.service.ts` `importCompiled`) — после пересборки секции сервис
подхватывает правку САМ, БЕЗ рестарта `sites`. Рестарт нужен только если
трогали сам `preview.service.ts`/`preview.controller.ts` (серверный TS-код),
не .astro-секции.

## Как чинить (порядок)

1. Открыть конструктор, реально включить/поменять настройку через UI (не
   через API вручную).
2. Посмотреть `site_revision.data.pagesData.home` в БД — какие ИМЕННО пропы
   легли после правки через UI.
3. Прогнать эти ТОЧНЫЕ пропы через `/preview/block` — воспроизвести баг
   изолированно.
4. Сравнить с тем, как аналогичное поле устроено в
   `themes/rose/src/components/sections/<Секция>.astro` — Rose эталон.
5. Чинить порт flux по образцу Rose.
6. Проверять снова ЖИВЬЁМ через конструктор (клик → превью), не только
   через `/preview/block`.

## Новая матрица проверки — `flux-baseline/settings-liveness3.mjs`

HTML реально меняется (LIVE) И ни один `[data-reveal]`-потомок не застревает

**Три ловушки, в которые сам скрипт попал при разработке (описаны в шапке
скрипта подробно)** — держать в голове при дальнейшей правке:
